# Changelog

## 0.7.7 — 2026-08-21

- **Fixed repeated launch clicks**: `-Open`, `-OpenWeb`, and `-Restart` now share a
  process-wide request mutex for the complete readiness flow. Once one launch is
  underway, later shortcut/tray clicks return immediately instead of creating
  competing PowerShell flows that can repeatedly start and stop `node.exe`.
- **Added tray restart**: the new **重新启动** menu item restarts the Harness service
  and desktop window while keeping the tray icon alive.
- **Reduced quit-to-reopen latency**: known desktop-window PIDs close directly, and
  normal single-node shutdown skips the full WMI process scan; the scan remains for
  legacy roots or multiple Node processes.

## 0.7.6 — 2025-xx-xx

- **Fixed: a console terminal flashed (or stayed visible) whenever the desktop
  was opened — at boot, via the desktop shortcut, and via the tray.** Root
  cause: the desktop shortcut, the logon task's companion action and the tray
  "打开" handlers launched `powershell.exe` with `-WindowStyle Hidden` as a
  *command-line argument*. PowerShell only honours that flag after its own CLR
  startup finishes, so the console window was created visible and stayed that
  way during startup — at boot under peak load the CLR cold-start is tens of
  seconds, which is exactly the "terminal pops up, then vanishes when the
  window finally appears" symptom. Every external PowerShell launch now goes
  through either `wscript.exe` + a generated VBS (`sh.Run cmd, 0, False`, which
  sets `SW_HIDE` at the Win32 level so the console is never created visible) or
  `Start-Process -WindowStyle Hidden` (the switch, same SW_HIDE guarantee):
  - the desktop shortcut now targets `wscript.exe` running `dsh-open.vbs`
    (generated by `Install-Shortcut`), with `-ShortcutOk` updated to match;
  - the logon task's second action now runs `wscript.exe` running a generated
    `dsh-companion.vbs` (falls back to plain PowerShell only if generation
    fails), and the Run-key last-resort value uses the same hidden launcher;
  - the tray "打开" and double-click handlers now use the `Start-Process`
    `-WindowStyle Hidden` switch instead of the argument.

- **Fixed: at boot the desktop window opened but the tray icon did not appear.**
  Root cause: `tray.pid` was written by the `-AutoStart` companion *before* it
  actually owned the tray, so it raced the tray that the host `apply()` spawns
  when it sees no tray; the two processes overwrote each other's `tray.pid` and
  contended for the `DSHDesktopTray` mutex. The tray entry's mutex handler also
  released an `AbandonedMutexException` acquisition (`ReleaseMutex()` in the
  catch) and then continued as "first", letting two trays coexist. `tray.pid`
  is now written only after the mutex is acquired (single owner), and the
  abandoned-mutex branch acquires without releasing; a redundant spawn now
  self-corrects to exactly one tray with a correct `tray.pid`.

- **Reduced the settings-page stutter.** `Close-AppWindow` now writes a
  `pid: 0` "closed" record instead of deleting `app-window.json`, so the host's
  fast path can answer "window not running" without cold-starting a
  PowerShell `-AppWindowActive` process every 5 s (the dominant lag source when
  the Settings page is open). The fast/slow TTLs were aligned with the client's
  5 s poll (`2000→5000` ms fast, `5000→15000` ms slow), and the watcher's
  permanent poll was relaxed from 200 ms to 500 ms.

- **Cut the reopen latency ("quit → reopen" ~10 s, tray reopen ~5-6 s).** The
  `-Open` flow serially cold-started several PowerShell sub-processes for WMI
  lookups (`Start-Job`), which stacked into seconds before the window appeared:
  - `Invoke-CimBounded` now runs the query in an **in-process runspace** with a
    hard `BeginInvoke`/`WaitOne` timeout instead of `Start-Job` — no more
    `powershell.exe` child per WMI call (measured ~7× faster in isolation);
  - `Get-HarnessNode`/`Get-HarnessRoot` do a cheap pure-Win32 `Get-Process`
    pre-check and skip WMI entirely when no `node`/`cmd` process exists (the
    common case right after a quit);
  - `Get-AppWindowProcess` only falls back to the CIM command-line match when
    `app-window.json` is **missing** — a present record (`pid: 0` or a stale
    PID) is a known "closed" state and no longer triggers a WMI scan;
  - the watcher writes its `watcher.ready` signal **before** the slow layout
    calc (snapshot first), so `-Open` launches the browser ~1 s sooner;
  - `-Open`/`-OpenWeb` now open the window/browser **first** and spawn a
    missing tray afterwards, so the visible result appears before the tray.

## 0.7.5 — 2025-xx-xx

- **Fixed: exiting left `node.exe` (the harness) resident in Task Manager.**
  Root cause: `Stop-Harness`'s kill loop was written as
  `foreach ($pid in $targets)` — `$PID` is PowerShell's read-only automatic
  variable (the current process ID), so assigning the loop variable throws
  "Cannot overwrite variable PID because it is read-only or constant". With
  `$ErrorActionPreference = 'SilentlyContinue'` that error is silently
  swallowed and the `taskkill` loop never runs — so the tray 退出 notified the
  pages and closed the window but never actually terminated the harness node
  process. Renamed the loop variable to `$targetPid`, restoring the kill. This
  also removes a latent root cause behind the earlier quit→reopen races: the
  old instance was never really killed, only masked by the self-heal/relaunch
  logic.

## 0.7.4 — 2025-xx-xx

- **Fixed: Settings "显示终端 / 隐藏终端" did nothing.** Root cause: the v0.7.3
  age-guard work added a `[datetime]$Cutoff` parameter to `Get-HarnessNode` /
  `Get-HarnessRoot`, and `Get-HarnessRoot` passed its unset (`$null`) cutoff
  through as `-Cutoff $null` — PowerShell then tried to convert `$null` to
  `System.DateTime` and threw a parameter-conversion error. With
  `$ErrorActionPreference = 'SilentlyContinue'` the error was silently
  swallowed, `Set-TerminalWindow` received no root process and returned
  without doing anything — so the button appeared dead (state.json still
  updated, POST still 200, window unchanged). Fixed by making `Cutoff`
  untyped (`$null` and real timestamps are both safe); the age guard itself
  is unchanged, so the boot auto-start and the quit→reopen race protections
  keep working — in fact the dying-instance observation path inside
  `Ensure-Harness` (silently dead since v0.7.3 for the same reason) works
  again as designed.
- **Surface real failures**: `Set-TerminalWindow` now distinguishes "harness
  not running" (silent success — the preference applies on next start, as
  designed) from "harness running but the console window could not be
  shown/hidden" (exit code 1 → the Settings page shows the error instead of
  doing nothing).
- Verified end to end on the affected machine through the real host route:
  show → visible, hide → hidden, show → visible, hide → hidden (window
  state checked via the console HWND), with `state.json` restored. Race
  regression suite: 12/12 pass.

## 0.7.3 — 2025-xx-xx

- **Fixed: quit → immediately reopen still failing (tray missing / harness
  inaccessible).** v0.7.2's protections had four remaining holes, all closed
  now:
  - **Quit marker is no longer force-cleared while the quitter is alive.**
    `quitting.tmp` now records the quitter's PID; `Wait-QuitFinished` only
    proceeds when the marker is gone **or** the quitter process has exited
    (crashed-quitter residue is cleared immediately). v0.7.2 cleared the
    marker after a fixed 20 s — a slow teardown (WMI scans can exceed 20 s)
    let `-Open` start a fresh instance while the old quit was still killing,
    and the new instance could be swept into the quit's kill snapshot. The
    wait now lasts up to 45 s and never races a live quitter;
  - **`Stop-Harness` age guard**: only processes that existed ≥6 s before the
    kill snapshot are terminated. Even if a stuck quitter eventually runs its
    kill pass, an instance spawned concurrently by `-Open` can never be
    killed;
  - **Quit order reversed**: the harness is stopped right after the (fast,
    no-sleep) page-close signal — the port frees within seconds instead of
    staying live through the whole SSE/window teardown, shrinking the race
    window; the 1.5 s fixed sleep in `Send-QuitSignal` was removed;
  - **`Ensure-Harness` self-heals while waiting**: every 15 s it re-checks —
    port down and no process (the fresh instance died or was killed) →
    relaunch under the launch mutex; port up but HTTP dead for >20 s (a
    dying/zombie leftover) → force-kill and relaunch once. No more blind
    60 s wait ending in "harness did not become ready";
  - **`Ensure-TrayRunning` verifies and retries**: it now first waits for a
    still-exiting old tray process to fully die (the new tray used to lose
    the `DSHDesktopTray` mutex race and exit instantly — the "no tray"
    symptom), then starts the tray and polls `tray.pid` + process liveness,
    retrying up to 3 times with stale-pid cleanup in between;
  - **`tray.pid` ownership**: a quitting tray only removes `tray.pid` when
    the file still contains its own PID, so it can never delete the record of
    a tray that took over during the quit.
- Verified: PowerShell parser clean (UTF-8 BOM preserved); sandbox race
  tests cover the quit-marker wait (mark with live quitter blocks, dead
  quitter clears), the age guard (young processes are skipped by
  `Stop-Harness`), the tray respawn verification, and the self-heal relaunch
  when a spawned instance dies.

## 0.7.2 — 2025-xx-xx

- **Fixed: quit → immediately reopen race.** Tray 退出 (or `-Quit`) followed
  within seconds by the desktop shortcut (`-Open`) could leave the harness
  inaccessible and no tray: the old instance was still dying when `-Open`
  probed it, so it was mistaken for "already starting" and nothing was
  relaunched (and no window/tray appeared). Four coordinated fixes:
  - **Quit marker**: `Invoke-Quit` writes `quitting.tmp` for the whole
    teardown; `-Open`/`-OpenWeb` wait for it to disappear (≤20 s, stuck
    markers are cleared) before starting anything — a reopen can no longer
    race a live shutdown;
  - **Teardown wait**: `Stop-Harness` snapshots all targets first (root +
    matching node processes) and kills them in one pass — a freshly started
    instance can no longer be swept up by a late scan — then waits (≤8 s) for
    the port to actually free;
  - **Dying-instance detection**: `Ensure-Harness` now observes a process
    found with the port down: if it exits (the dying leftover), the harness is
    relaunched immediately; if it survives 20 s without the port (wedged), it
    is force-killed and relaunched;
  - **Tray restore**: `-Open`/`-OpenWeb` respawn the tray when it is missing
    (e.g. open via shortcut after quitting the tray), so the tray always
    comes back;
  - **Launcher fallback**: `-AutoStart` trusting the wscript launcher now
    watches the port for ≤15 s — if it never opens (the launcher's node died,
    or another app's `node.exe` happened to be running at logon), the harness
    is started anyway, so the service is guaranteed.
- **The logon task now has two sequential actions**: ① `wscript.exe
  dsh-autostart.vbs` (starts the service directly, <1 s cold start) and ②
  PowerShell `-AutoStart` (desktop window + tray, skips launching when the
  service is already coming up). If `wscript.exe` is blocked by policy,
  action ② still brings the service up — no more silent single-point
  dependency. The VBS was simplified accordingly (node start only).
- Verified: function-level tests for the generated VBS and task XML (two
  actions, priority 5, logon trigger); sandbox race tests confirm `-Open`
  waits while `quitting.tmp` exists and proceeds right after it is removed,
  and the 15 s launcher fallback kicks in when the port never opens.
  (Full end-to-end window-open under the sandbox is not measurable — the
  sandbox kills deep process trees — but the real machine's `-Open` was
  measured at 7.0 s readiness before these changes.)

## 0.7.1 — 2025-xx-xx

- **Fixed: the desktop window/UI still opened slowly even though the logon
  task fired on time.** Measured on the affected machine (2026-08-16 boot):
  task fired at sign-in (+0 s) → the `-AutoStart` PowerShell took **27 s just
  to cold-start** (PS 5.1 CLR init under the peak logon load of ~100 startup
  apps + Defender) → only then was node spawned, and the service took another
  ~48 s to become ready — so the window appeared at +30 s and the UI at +80 s.
- **The logon task action now runs `wscript.exe` with a generated
  `dsh-autostart.vbs` launcher**: wscript cold-starts in <1 s (no .NET CLR
  init), immediately starts the harness service hidden (`node <entry> web`,
  entry/DSH_HOME/cwd embedded from the current `harness.json`), then starts
  the PowerShell companion (desktop window + tray) as before. Measured under
  simulated boot load: **wscript spawns node in ~0.8 s** (vs the 27 s
  PowerShell cold start). `-AutoStart` now skips its own `Start-Harness` when
  the launcher marker (`harness-launch.tmp`) exists **and** a `node` process
  is already running (pure Win32 `Get-Process`, no WMI) — verified: no
  duplicate instance is spawned, the marker is removed right after the
  decision, and the window still opens. The launcher is regenerated on every
  `Set-AutoStart` (the entry changes when the harness updates) and the task
  action falls back to plain PowerShell if generation fails.
- **Task priority raised 7 (below normal) → 5 (normal)** so the boot chain no
  longer starves behind the startup queue.
- The task on the affected machine has been re-registered with the new
  `wscript` action (method remains `task`); next logon starts the service at
  ~+2 s instead of ~+32 s.

## 0.7.0 — 2025-xx-xx

- **Fixed: login auto-start was still slow because the task migration never
  actually worked.** v0.6.0 registered the logon task through
  `schtasks /Create /TR "…\"…\""` — but schtasks does **not** support
  backslash-escaped quotes in `/TR`; it parses them literally and fails with
  "The system cannot find the path specified", so every registration silently
  fell back to the `HKCU Run` key and the boot stayed stuck behind Explorer's
  startup-item queue (measured again on the affected machine: Run key fired
  ~60 s after kernel boot, harness ready ~2.6 min after boot).
  Registration now tries, in order:
  1. **Schedule.Service COM** (no command-line quoting at all, does not depend
     on `schtasks.exe`), then
  2. **`schtasks /Create /XML`** (quotes inside the XML task file need no
     escaping; UTF-16 task file written next to the script and removed after),
     then
  3. the Run key as the last-resort fallback, with the failure recorded in
     `autostart-method.json` so it stays diagnosable.
  The task is verified (exists + logon trigger) before the Run key is removed;
  the auto-migration in `-AutoStart` still runs at every boot while the Run
  key is present, so machines that were left on the old path heal themselves
  at the next logon. This machine has now migrated: `autostart-method.json`
  reports `task` and the Run key is gone.
- **The boot open path no longer touches the CIM fallback channel**:
  `Open-HarnessWindow -Boot` skips the "is a window already open" CIM query
  (the stale record was already purged), avoiding one `Start-Job` PowerShell
  cold start and up to 8 s of WMI wait while WMI is still coming up.
- **New `-AutoStartDiag` mode**: reports whether each registration method
  works, whether the task exists, and the current Run-key/method state — run
  `powershell -File "%LOCALAPPDATA%\dsh-desktop\dsh-tray.ps1" -AutoStartDiag`
  to diagnose.
- Boot-chain timing facts for the affected machine (2026-08-16 boot):
  kernel boot 15:32:25 → Run key fired the tray script 15:33:26 (+61 s,
  startup queue) → harness node spawned 15:33:27 → harness ready 15:35:01
  (+94 s cold boot under load; ~6.5 s warm). With the logon task the tray
  chain starts at sign-in instead of after the queue, and the desktop window
  with the built-in boot page is visible within seconds of logon while the
  harness cold-boots in the background.

## 0.6.0 — 2025-xx-xx

- **Login auto-start now uses a Task Scheduler logon trigger instead of the
  `HKCU Run` key.** Measured on the affected machine, the Run key fired the
  tray script **~2.3 minutes after logon**: Explorer executes Run-key entries
  only after the user session's startup queue, and this machine boots ~100
  startup processes (Lenovo/NVIDIA/Doubao/Youdao/QQ/KuGou/…), so the harness
  was starved for minutes. The Task Scheduler service triggers the logon task
  immediately at sign-in, independent of Explorer's startup queue — the harness
  now starts right away. Creation falls back to the Run key when `schtasks`
  fails (e.g. locked-down environments); toggling auto-start migrates
  automatically. **Migration is fully automatic**: an `-AutoStart` run that is
  still triggered by the Run key detects the missing task, creates it and
  removes the Run key by itself (after opening the window, so it never delays
  the current boot), and writes `autostart-method.json` (`task` / `runkey` /
  removed on disable) for diagnostics.
- **Login auto-start is now fast (seconds, not minutes)**. Measured on the
  affected machine: the harness node used to start ~2.5 min after logon and the
  desktop window followed later. Three compounding boot-time costs were removed:
  - **No more C# compilation at boot**: the two `Add-Type -TypeDefinition` blocks
    (DSHNative/DSHShell) were compiled by every PowerShell invocation (each cold
    `csc` run costs tens of seconds right after logon). They are now lazy-loaded
    and **compiled once into hash-stamped DLLs** (`dsh-native-<hash>.dll`,
    `dsh-shell-<hash>.dll`) in the app dir; every later process — the watcher
    included — just loads the cached assembly. Simple modes (`-ShortcutOk`,
    `-AutoStartOn`, `-AutoStartOff`, …) no longer compile anything.
  - **No unbounded WMI waits at boot**: every `Get-CimInstance` call now goes
    through `Invoke-CimBounded` (background job + timeout, worst case ~8 s)
    and fast pre-checks skip the query entirely when the port is already
    listening or no whitelisted browser process exists. The old code could
    block for minutes while the WMI service was still starting.
  - **`-AutoStart` no longer waits for HTTP readiness**: it launches the harness
    and immediately opens the desktop window with a new built-in **boot page**
    (`boot.html` — whale spinner, polls the service, auto-redirects), so the
    window is visible within seconds of logon while the harness cold-boots in
    the background. The stale `app-window.json` record from the previous
    session is purged before opening, so the open flow never falls into the
    WMI fallback channel at boot.
  - **Local probes bypass the system proxy** (`$req.Proxy = $null` in
    `Test-HarnessHttp`), so a Clash-style proxy can never delay readiness polls.
- **Harness startup is no longer blocked by the plugin's own PowerShell work**:
  the registry auto-start sync and desktop-shortcut repair now run in the
  background (they used to be awaited serially, each spawning a PowerShell
  process that could take tens of seconds at boot).
- **The harness no longer kills the boot tray**: `apply()` used to
  `stopTray()` + respawn the tray on every start — racing the Run-key tray that
  is mid-`-AutoStart` (and paying another PowerShell cold start). It now only
  spawns the tray when none is running; the Run-key tray is left to finish its
  boot flow. A stale tray version is replaced naturally at the next logon.
- **`dsh-tray.ps1` must be saved as UTF-8 with BOM** (PS 5.1 reads BOM-less
  files as ANSI, garbling the Chinese comments/strings and breaking parsing).

## 0.5.0 — 2025-xx-xx

- **Reliable desktop/web state detection (no WMI dependency)**: `-AppWindowActive`,
  `Get-AppWindowProcess` and `Close-AppWindow` no longer depend on WMI. The PID
  recorded by `-Open` is now the primary channel — and the `-WatchAppWindow`
  watcher **self-heals the record to the real window-owner PID** after the
  window appears — with the CIM command-line match kept as a best-effort
  fallback in normal environments. The Settings **切换桌面端 / 切换网页端**
  button and the "桌面窗口" status card now always reflect the real mode, and
  switching to web reliably closes the desktop window, even where WMI is
  unavailable. The Settings page also **refreshes state every 5 s** while open
  (paused while hidden/busy), so the label stays truthful when the window is
  opened or closed from the tray or the desktop shortcut.
- **Window size per user spec**: the desktop window now opens at the **1352:972
  ratio** — width = 70.42% of the primary work-area width, height keeps the
  ratio (1352×972 on a 1920×1080 display), **centered on the monitor**, min
  **960×690 DIP** (ratio-consistent), still fully DPI-aware.
- **Dedicated browser profile for the app window**: the window launches with its
  own `--user-data-dir`, so the launched process *is* the window owner. This
  fixes the cases where an already-running Edge hijacked the launch (dead broker
  PID recorded, `--window-size` ignored, stale session bounds restored — the
  931×1005 window) and makes detection/closing deterministic.
- **Whale icon on the desktop window**: the desktop shortcut gets the
  `System.AppUserModel.ID`/`RelaunchIconResource` properties (IPropertyStore),
  the window launches with `--app-user-model-id=DSHDesktopApp`, and the watcher
  applies `WM_SETICON` with the whale `.ico` — the taskbar, Alt-Tab and the
  window itself show the DeepSeek Harness whale instead of the Edge logo.
- **Switching modes closes the previous window**: `-Open` first sends the quit
  signal so open Harness browser pages close themselves, then opens the desktop
  window; `-OpenWeb` closes the app window before opening the default browser.
- **Engine follows the user's default browser**: the app window now prefers the
  **default browser when it is Chromium-based** (Chrome/Edge/Brave/Opera/Vivaldi,
  resolved from the `http` UserChoice ProgId), falling back to **Edge** (ships
  with Windows 10/11) then **Chrome**; only when no Chromium browser exists at
  all does it open the default browser as a normal window. The window stays
  fully isolated from the user's normal browsing session via its dedicated
  `--user-data-dir`, so browser extensions, notifications and sign-in prompts
  never leak into it.
- **Whale icon made bullet-proof**: the window is launched **through a whale-icon
  `.lnk`** (`dsh-appwindow.lnk`, with `System.AppUserModel.ID` properties), so
  Windows uses that shortcut's icon and name for the taskbar button; a matching
  Start Menu shortcut anchors the AppUserModelID lookup, and the watcher still
  applies `WM_SETICON` to the window itself.
- **Tray quit now closes the desktop window too**: the app-mode window cannot
  close itself via script (`window.close()` is blocked for `--app` windows), so
  the shared quit path (`-Quit` and the tray menu 退出) now explicitly calls
  `Close-AppWindow` (record PID + CIM fallback) after signaling the browser
  pages — the desktop window and the browser tabs close together.
- `Send-QuitSignal` only waits for page close when the signal was delivered.

## 0.4.0 — 2025-xx-xx

- **Window layout per spec**: the desktop window now opens at **72% × 80% of the
  primary screen work area** (taskbar excluded), **horizontally and vertically
  centered**, with a **960×600 DIP minimum size** enforced while the window is
  open. All sizing is **DPI-aware** (125%/150% scaling supported): the script
  becomes a per-monitor DPI-aware process, measures the work area in physical
  pixels, and converts to the DIP values Edge/Chrome expect.
- **No startup flicker or position shift**: the window launches minimized with
  its final size/position pre-set; a hidden `-WatchAppWindow` watcher process
  hides the window immediately, waits for the page title to be ready (first
  content render), then restores it at the exact centered size. The watcher
  then enforces the minimum size (maximize excluded) and exits when the window
  closes.
- **Toggle state check fixed for restricted environments**: `-AppWindowActive`
  and `Close-AppWindow` no longer depend solely on WMI. Detection now uses a
  dual channel — CIM command-line match (`--app=<origin>`) plus the PID recorded
  by `-Open` (verified alive, chrome/msedge, and with a visible main window) —
  so the Settings **切换桌面端 / 切换网页端** button always reflects the real
  mode and switching to web reliably closes the window.
- **Settings toggle now polls**: after switching, the Settings page polls the
  snapshot (up to ~40s) until the window state matches the target, so the
  button label flips without a manual reload.
- **Edge install-path fix**: `${env:ProgramFiles(x86)}` is now expanded
  correctly, so Edge installed under "Program Files (x86)" is found.
- **Diagnostics**: `-LayoutInfo` prints the computed layout (work area, size,
  position, scale); `open-state.json` records the applied window geometry.

## 0.3.0 — 2025-xx-xx

- **Desktop window is the default and only open mode**: the "open method"
  setting (`appWindow`) was removed. `-Open` always launches local Edge/Chrome
  in `--app` mode with a default **16:9** window (1600×900), falling back to the

  web mode and **切换网页端** in desktop mode. Switching to web closes the

  `-AppWindowActive` companion mode reports whether the desktop window is
  running, and a "桌面窗口" status card shows the live mode.

## 0.2.0 — 2025-xx-xx

- **Boot speed**: the tray now starts the harness directly with `node <entry> web`
